# Garmin App Remote

- **Garmin App Remote (#80, in progress on `garmin-app-remote`).** NimBLE-Arduino is pinned at **1.4.3** in `[common]`; `[s3]` sets `CONFIG_BT_NIMBLE_MAX_CONNECTIONS=4` and a 6144 B host task stack (host on core 0, off loop()'s core). Unreferenced, it adds nothing to either image. WiFi/BT software coexistence is on in the core's sdkconfig. **RMT gate passed on V1 (2026-10-02)**: Dev Mode STA + BLE advertising + 2 subscribed centrals (FR970, a phone) at 20 notifies/s + fob presses, in a match: 207,844 refills, 0 bails, 0 stale, max 5 us late; NimBLE took 51.7 KB heap, min free 191 KB. A raw `ble_gattc_notify_custom` from loop() took up to ~1 ms.
- `src/Garmin/` core is pure and header-only (no Arduino/NimBLE/Preferences), host-tested and shipped as is: `GarminProtocol.h` (constants, enums, frame builders, roster CRC-32, state chunking), `WatchCommand.h` (parse: too short -> MALFORMED, trailing bytes ignored per spec 2, `0x0C` unused -> UNKNOWN_CMD), `WatchState.h` (body builder; views use its typed setters, never raw bytes), `Sha256.h` (portable SHA-256/HMAC + constant-time compare; < 0.5 KB stack, it runs in the NimBLE host task), `GarminData.h` (the 174 B `"gar"` blob in namespace `"ns"`, never a `PrefsData` field, and `GarminPairingStore`'s LRU slots; `load()` drops a slot whose `used` is not 0/1 and renumbers the LRU counters). Suites `test_garmin_protocol` / `test_garmin_auth` / `test_garmin_pairing` hold every spec 16.x vector; run them after touching `src/Garmin/`.
- **`GarminService`** (`src/Garmin/GarminService.*`) is the only NimBLE user; the protocol state is the pure, host-tested `GarminLink.h` (`test_garmin_link`), the blob I/O `GarminStore.h`. Off by default; `setup()` calls `begin()` last, only when the stored flag is on, and `loop()` keeps BLE in step with the flag. Init and deinit run in one-shot core-0 tasks, never in `setup()`/`loop()`; a failure is logged and leaves the feature off. An `RTC_NOINIT` marker set across init keeps BLE off **until a power cycle** after any reset inside init (NimBLE `ESP_ERROR_CHECK`s abort), and init is not tried under 80 KB internal heap - a sealed V1 never crash-loops out of OTA reach. Host-task callbacks only call `GarminLink` under one portMUX: byte copies only, never NVS, `printLn`, NimBLE or an HMAC (it runs outside the lock, then the key is re-checked). `loop()` does everything else: per-connection notifies via `ble_gattc_notify_custom` (never `NimBLECharacteristic::notify()` on core 1), terminates, advertising updates, the deferred `"gar"` write. One key per connection; re-issuing a slot drops the connection that proved its old key; only a delivered key restarts the 10 s unauthenticated timeout.
  - `main.cpp` applies **one watch command per 50 ms tick**, after the long-C branch and never in a tick where long C went back, through `DeviceMode::handleWatchCommand` (BACK = `goBack()`, false -> WRONG_SCREEN). Busy screens (`WatchSport::fromModeState().viewDescribes` false: CONFIG, booting) take no command - `ConfigMode::goBack()` saves and leaves; PROFILE takes BACK only. APPLIED plays the fob's sound. Under an Overlay every queued command is answered BUSY. The state is described after `deviceMode->loop()` and published only on change. Test the board from a PC with `helpers/garmin_client.py` (bleak; keys in `~/.scoreboard-garmin/`, never in the repo).
  - **Watch commands reach the same named view methods as the fob** (`togglePlayer`, `startTournament`, `cycleLeft/Right`, `swapSides`, `startMatch`, `setPair`, `score`, `undo`, `skip`, `nextGame`, `selectEntry`, `focusEntry`, `focusOption`, `exitToMenu`); FOCUS (`0x0E`, `target` u32 = sport on MENU, uid or 0 = START on CHOOSE_PLAYERS) is the fob's A/B cursor move through the same method, never acts, and `applyWatchCommand()` acks it APPLIED **without** `gBuzzer.trigger()` (a watch scroll is silent); CHOOSE_PLAYERS' state carries the cursor uid at offset 12, so fob scrolls reach the watch too; the fob handler keeps its own debounce and `preventTriggerForMs`, `handleWatchCommand` only validates arguments (INVALID / WRONG_SCREEN). `DeviceMode::handleWatchCommand` -> `WatchSupport::route`: BUSY while `viewChangePending()` (sport modes: `state != previousState`), then BACK = `goBack()`, else the view. PROFILE's BACK is its C/D exit, not `goBack()` (long C there stays a no-op). `describeForWatch` sits beside each view's render code, court side only; `publishWatchState()` skips a pass with a view swap pending. `test_garmin_views` hosts the real views through `view_stubs.h` (pre-defined include guards) - add a stub there for any new display call.
  - **CONFIG has 6 rows** (LED, BUZZER, Dev Mode, GARMIN, RESTART, COFNIJ). GARMIN is a sub-menu entry, not a switch (user's call, 2026-10-03: a switch-looking row that opens a menu holding another switch confused): no tickbox, blue on the LEDs and V1 bar, LED word `GAr` (the 4-letter prefix needs an M); D opens the sub-screen. The on/off is only its AKTYWNY row (`GarminService::isEnabled()`, the `"gar"` blob, never `PrefsData`), LED word `on` / `oFF`. `ConfigMode` has its own deferred state machine (`ConfigModeState`: Menu / Garmin / GarminPairing); long C walks pairing -> GARMIN -> CONFIG -> menu and only the last step saves `PrefsData`. `GarminView`: AKTYWNY (live `setEnabled`), PARUJ (only while `running()`), ZAPOMNIJ (first D arms `NA PEWNO?`, a second D forgets, any other key disarms), COFNIJ; footer = paired / connected counts. `GarminPairingView` opens the window in its constructor and closes it in its destructor (every exit), and leaves on its own once a newly paired watch has **authenticated** (`completedPairings()`), never at key delivery - closing wipes the key reply. The e-paper countdown steps by 30 s (a 1 s step would near `MAX_PARTIALS`); the OLED shows exact seconds.
- **Active roster (#85, spec 12).** `setup()` prebuilds both wire tables and CRCs (`setRoster(RosterKind::Players|Teams, ...)`); `buildDeviceMode()` selects the kind first (`useRoster(WatchSport::fromModeState(mode).roster)`, the `roster` column of `WatchSport`'s table is the only sport -> kind mapping). `GarminLink` applies it with the next **published** state (`preparePushes(state)`), never earlier: an ack-only push (overlay) or a host-task STATE read in between would pair the old sport with the new `rosterVersion`, and the watch would cache the roster under the wrong kind. `useRoster` only flips an index under the lock (no copy, no CRC); a version change alone pushes (`pushedRosterVer`). No wire change: an old watch just re-reads on each switch.
- The Garmin watch as a BLE remote was researched first (task #66): feasible on both boards, ~0.5 s latency fixed by Connect IQ, needs explicit watch<->board pairing. Read `docs/garmin-remote-poc.md` before any BLE work; the Garmin App Remote wire protocol (advertising, GATT, auth, pairing, commands, state) is specified in `docs/garmin-protocol.md` - #80 and #81 implement it, change it there first.
